# write-prd Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task.
> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a `write-prd` Agent Skill that turns a raw feature idea
into a Vietnamese-first mini PRD at epic/feature scope, with
`less`/`normal`/`fully` templates and a filename-safe write flow.

**Architecture:** A short `SKILL.md` selects one of three copy-paste
templates from `assets/` and loads three focused references on demand.
The templates are strict supersets by level; the references explain
section quality, vertical-slice capability decomposition, and the
pre-output checklist. Registration goes in `.skills.json`, `README.md`,
and `CHANGELOG.md`; no CI or version changes.

**Tech Stack:** Markdown, Agent Skills frontmatter, `jq`, `grep`,
markdownlint-cli2, git.

**Spec:** `docs/superpowers/specs/2026-10-28-write-prd-design.md`

## Global Constraints

- Frontmatter keys: `name`, `description`, `license`, `metadata`;
  `parameters.detailed_mode` enum `["less", "normal", "fully"]`, default
  `"less"`.
- Output language is Vietnamese unless the user requests otherwise;
  headings use `Tiếng Việt (English)` pairs fixed by the spec.
- PRD scope stops at feature/capability. No tasks, estimates, branches,
  PRs, implementation file paths, or hour ranges.
- Default output path is `docs/prd/<slug>.md`; ask for the filename
  before writing; never overwrite without explicit confirmation.
- `less` keeps assumptions and `TBD` inline; `normal`/`fully` use the
  Assumptions and Open Questions sections.
- Section order: Epic Overview -> Assumptions -> Open Questions ->
  Features -> UI/UX -> Data & Integration -> Risks -> Rollout ->
  Analytics -> NFR -> Traceability -> Sign-off -> Handoff.
- UI/UX and Data & Integration are epic-wide; add `### F0x - <Feature
  Name>` grouping only when the epic has more than one feature.
- `.skills.json` version stays `1.2.0`; new work goes under
  `[Unreleased]`. Do not create a tag or release.
- Do not modify `.github/`, `CONTRIBUTING.md`, existing skills, or
  `.agents/**`.
- Every new Markdown file must pass markdownlint with the repository
  config.

## Review Focus

1. User asks for a PRD without naming a file -> the agent asks for the
   filename and writes nothing yet.
2. The chosen file already exists -> the agent asks before overwriting
   and leaves the original untouched until confirmed.
3. An epic has several features -> UI/UX and Data sections group content
   under `### F0x` without duplicating or dropping sections.
4. The user cannot supply a metric or integration detail -> the PRD
   records `TBD (owner: ...)` or an explicit assumption, never an
   invented value.
5. No level is requested -> `less` is used, and `normal`/`fully` contain
   every lower-level heading in the same relative order.

**Files:**

- Create: `skills/write-prd/references/capability-decomposition.md`

**Interfaces:**

- Produces: the boundary and slicing rules used by `SKILL.md` step 4.
  Defines Epic/Feature/Capability/Task and states that tasks belong to
  `kanban-task-breakdown`.

- [ ] **Step 1: Write the reference**

Include:

1. `# Capability Decomposition Guide`.
2. A boundary table: Epic (business outcome, weeks), Feature
   (user-visible area, days-weeks), Capability (behavior plus rules,
   one PRD bullet group), Task (implementation unit, <= 1 day, owned by
   `kanban-task-breakdown`).
3. The sizing guidance: one to five features per epic, two to five
   capabilities per feature.
4. Three vertical-slice methods: user journey steps, roles/personas,
   user-visible states. Explain why layer-based splitting (DB ->
   service -> API -> UI) is task-level and must not appear in a PRD.
5. A naming rule: verb + object + outcome, for example "Apply a coupon
   at checkout", not "Coupon service".
6. Three worked examples: checkout, notifications, admin reporting.
7. An anti-pattern table mapping task phrasing ("build API endpoint",
   "create table", "refactor service", "add unit tests") to a
   capability-level rewrite or "defer to kanban".
8. A handoff note.

**Interfaces:**

- Produces: the pre-output gate used by `SKILL.md` step 6. Every item
  has a pass condition the agent can check against the draft.

- [ ] **Step 1: Write the checklist**

Use `# PRD Quality Checklist` and checkbox items grouped as:

- Scope: level matches request; no tasks, estimates, branches, PRs, or
  implementation file paths; capability count in range.
- Evidence: persona is specific; objective states current -> desired;
  metrics have baseline/target, timeframe, source, or
  `TBD (owner: ...)`; problem statement names who is affected and why
  now.
- Capability quality: every capability has a concrete example; business
  rules name condition, precedence, limits, permissions, and failure.
- Acceptance: DoD items are verifiable; test criteria use
  `condition -> observable result` and cover the level's required
  happy/edge/error/permission cases.
- Surfaces: UI placement, interactions, and required states; data
  inputs, APIs, mapping/contracts/failure behavior at the selected
  level.
- Completeness: out of scope is non-empty; assumptions and open
  questions are honest; handoff line present.
- Delivery: Vietnamese unless requested; filename asked before write;
  overwrite confirmed; written path reported.

Each item must state what "pass" looks like in one line.
